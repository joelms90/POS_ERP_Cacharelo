Why we need production secrets

A short explanation of the current risk, how Secret Manager fixes it, and what changes for the team.

Today

The production API has no configured secret values.

Admin protection

Without ADMIN_PASSWORD, the API falls back to a value embedded in source code. Anyone who knows or guesses it could access protected administration actions.

Login signing

Without JWT_SECRET, login tokens are signed with a development fallback. That makes token security weaker than production should allow.

The application still works. The issue is that its locks are using predictable spare keys instead of private keys controlled by us.

The solution

Secret Manager stores the real keys outside the code and outside Git.

1 · CreateWe create two long, random secret values in Google Cloud.
→
2 · GrantOnly the Cloud Run service gets permission to read the values.
→
3 · AttachCloud Run injects them as JWT_SECRET and ADMIN_PASSWORD when the API starts.
→
4 · RunThe API uses those private values. They never appear in source control, the browser, or normal logs.

What changes for people

One planned logout is the only user-visible effect.

After deployment

New logins and admin access use private production secrets. The new logging feature can safely receive and investigate app errors by sucursal.

JWT rotation

Changing JWT_SECRET invalidates existing login tokens. Every active user will need to sign in again once. No business data is deleted.

Approval plan

Controlled rollout, with clear checks.

  1. Enable the Google Secret Manager API.
  2. Create the two random secrets and give only Cloud Run access.
  3. Deploy the API with the secret references; users log in again.
  4. Deploy admin and POS logging builds.
  5. Send one controlled test error and confirm it appears in the daily logging view.

Decision needed: approve enabling Secret Manager and the one-time sign-out caused by rotating the JWT signing key. Deployment happens only after that approval.
